# Сервис согласования макетов

Приложение для согласования дизайн-макетов между дизайнером и
клиентом: учёт макетов, комментариев клиента, статусов, версий и
сроков согласования. Консольная версия (ПР3) дополнена
веб-интерфейсом на Django (ПР5), страницы которого формируются
шаблонами Django (ПР6). В ПР7 данные перенесены в реляционную базу
SQLite, а страницы сайта получают их SQL-запросами.

## Используемые технологии

- Python 3;
- Django 5.2 — веб-фреймворк;
- Django Template Language (DTL) — шаблоны страниц;
- HTML5 — разметка веб-страниц;
- CSS3 и Bootstrap 5.3 — оформление страниц (Bootstrap подключается
  через CDN, собственный CSS — как статический файл);
- JavaScript — небольшое поведение интерфейса;
- SQLite и модуль `sqlite3` — реляционная база данных и SQL-запросы;
- pytest — автоматизированные тесты;
- flake8 — проверка качества кода.

## Назначение

Приложение решает задачу упорядочивания процесса приёмки работы:
дизайнер отправляет макет на согласование с указанием срока, клиент
оставляет комментарии и принимает решение — утвердить макет или
отправить на доработку. Все замечания, версии и статусы хранятся в
одном месте, что исключает потерю правок в почте и мессенджерах.

## Целевая аудитория

- дизайнеры и дизайн-студии, сдающие макеты заказчику;
- клиенты (заказчики), принимающие работу и оставляющие замечания;
- менеджеры проектов, контролирующие сроки согласования.

## Предметная область

Дизайнер создаёт макет и отправляет его клиенту на согласование,
указывая срок ответа. Клиент оставляет к макету комментарии и
переводит макет в один из статусов: «На согласовании», «На доработке»
или «Утверждён». При отправке на доработку версия макета
увеличивается, и цикл повторяется до утверждения. Утверждённый макет
повторно не утверждается и не отправляется на доработку.

## Основные классы

### Participant — участник согласования

Базовый класс для дизайнера и клиента.

Атрибуты: `id` — идентификатор; `name` — имя; `email` — почта.

Методы: `role` — свойство с названием роли; `from_data()` — создание
объекта из данных JSON; `to_data()` — преобразование в данные для
сохранения; `__str__()` — строковое представление.

### Designer — дизайнер

Наследник `Participant`, автор макета. Переопределяет свойство
`role`, поэтому один и тот же вызов `str()` для дизайнера и клиента
даёт разный результат.

### Client — клиент

Наследник `Participant`, заказчик, согласующий макет.

Дополнительный атрибут: `company` — организация клиента.
Переопределены `role`, `from_data()`, `to_data()` и `__str__()`;
`to_data()` вызывает реализацию базового класса через `super()`.

### Layout — макет

Объект согласования. Хранит ссылки на объекты `Designer` и `Client`.

Атрибуты класса: `STATUS_REVIEW`, `STATUS_REVISION`,
`STATUS_APPROVED` — возможные статусы, общие для всех макетов.

Атрибуты объекта: `id`, `title`, `designer`, `client`, `sent_date`,
`approval_days`, `version`, `_status`.

Методы: `status` — свойство, доступ к статусу только для чтения;
`deadline` — свойство, срок согласования рассчитывается из даты
отправки; `is_approved` — свойство-признак утверждения;
`days_left()` — число дней до окончания срока; `approve()` —
утверждение макета; `send_to_revision()` — отправка на доработку с
увеличением версии; `from_data()`, `to_data()`, `__str__()`.

### Comment — комментарий

Замечание клиента к конкретной версии макета. Хранит ссылки на
объекты `Layout` и `Client`.

Атрибуты: `id`, `layout`, `author`, `text`, `date`,
`layout_version`.

Методы: `is_valid_text()` — статический метод проверки текста;
`from_data()`, `to_data()`, `__str__()`.

## Взаимодействие объектов

    Designer ──┐
               ├──> Layout <──── Comment ────> Client (автор)
    Client ────┘

Макет связывает дизайнера и клиента: `layout.designer.name`,
`layout.client.company`. Комментарий связан с макетом и его автором:
`comment.layout.title`, `comment.author.name`. Связи между объектами
хранятся в оперативной памяти как ссылки, а в JSON-файлах — как
идентификаторы (`designer_id`, `client_id`, `layout_id`,
`author_id`).

## Страницы веб-интерфейса

| URL | Имя маршрута | View-функция | Шаблон |
|-----|--------------|--------------|--------|
| `/` | `homepage:index` | `homepage.views.index()` | `homepage/index.html` |
| `/layouts/` | `layouts:list` | `layouts.views.layouts()` | `layouts/layout_list.html` |
| `/layouts/search/` | `layouts:search` | `layouts.views.search()` | `layouts/search.html` |
| `/layouts/overdue/` | `layouts:overdue` | `layouts.views.overdue()` | `layouts/overdue.html` |
| `/layouts/statistics/` | `layouts:statistics` | `layouts.views.statistics()` | `layouts/statistics.html` |
| `/layouts/<int:layout_id>/` | `layouts:detail` | `layouts.views.layout_detail()` | `layouts/layout_detail.html` |
| `/comments/` | `comments:list` | `comments.views.comments()` | `comments/comment_list.html` |
| `/comments/<int:comment_id>/` | `comments:detail` | `comments.views.comment_detail()` | `comments/comment_detail.html` |

Страницы формируются шаблонами Django: view-функции выполняют
SQL-запросы к базе SQLite (ПР7), собирают словарь контекста и
вызывают `render()`. HTML в Python-коде не формируется.

Если макет или комментарий с указанным идентификатором не найден,
страница возвращает код статуса 404 с сообщением «Макет не найден» /
«Комментарий не найден». Для адресов, которым не соответствует ни
один маршрут, используется собственная страница 404
(`handler404 = "homepage.views.page_not_found"` в корневом
`urls.py`, шаблон `templates/404.html`); она отображается при
`DEBUG = False`.

## Шаблоны Django

### Базовый шаблон и наследование

`templates/base.html` содержит общую структуру всех страниц:
объявление документа, `<head>` с Bootstrap и собственным CSS,
шапку с логотипом и навигацией, контейнер страницы, подвал и
подключение JavaScript. В нём объявлены блоки:

    {% block title %}...{% endblock %}
    {% block content %}...{% endblock %}

Дочерние шаблоны наследуют его через `{% extends "base.html" %}` и
переопределяют блоки `title` и `content`.

### Включаемые шаблоны

Повторяющиеся фрагменты вынесены в отдельные шаблоны и подключаются
через `{% include %}`:

- `templates/includes/navigation.html` — навигация сайта (в
  `base.html`);
- `layouts/includes/layout_card.html` — карточка макета в списке;
- `layouts/includes/layout_status.html` — цветной бейдж статуса
  макета (в карточке и на странице макета);
- `comments/includes/comment_item.html` — строка комментария (в
  списке комментариев и на странице макета).

### Контекст, циклы и условия

View-функции передают данные в шаблон через словарь контекста,
например `{"layouts": sort_layouts(layouts_list)}`. В шаблонах
используются циклы `{% for %}` с обработкой пустой коллекции
`{% empty %}` и условия `{% if %}`: статус макета, срок согласования
(утверждён / истёк / осталось N дней), наличие найденного объекта.

### Фильтры шаблонов

- `{{ layouts|length }}` — количество макетов и комментариев;
- `{{ layout.title|default:"Без названия" }}` и
  `{{ layout.client.company|default:"частное лицо" }}` — значение по
  умолчанию;
- `{{ layout.deadline|date:"d.m.Y" }}` — формат даты;
- `{{ comment.text|truncatechars:60 }}` — сокращение длинного текста
  в списке.

### Именованные URL и пространства имён

В `urls.py` приложений заданы `app_name` (`homepage`, `layouts`,
`comments`) и имена маршрутов `list` / `detail`. Ссылки в шаблонах
строятся тегом `{% url %}`, например
`{% url 'layouts:detail' layout.id %}`, а не жёстко заданными
адресами.

### Статические файлы

Собственные статические файлы лежат в
`homepage/static/homepage/`:

- `css/style.css` — оформление шапки, навигации, карточек макетов и
  комментариев, статусов, подвала;
- `js/main.js` — вывод текущего года в подвале и подсветка активного
  пункта меню;
- `img/logo.png` — логотип сервиса в шапке.

В `base.html` они подключаются через `{% load static %}` и
`{% static '...' %}`.

## Основные операции

### Используется в веб-интерфейсе (ПР5–ПР7)

- просмотр списка макетов с сортировкой по сроку согласования;
- поиск макетов по части названия и фильтрация по статусу (ПР7);
- просмотр макетов с истёкшим сроком на выбранную дату (ПР7);
- страница статистики: количество макетов по статусам и дизайнерам,
  комментарии по макетам, макеты без комментариев (ПР7);
- просмотр карточки макета и комментариев к нему;
- расчёт оставшегося срока согласования на текущую дату;
- просмотр списка комментариев и карточки комментария;
- статистика по статусам макетов на главной странице.

### Отложено до следующих работ

Эти операции реализованы в ПР3 и работают в консольной версии.
В веб-интерфейсе они появятся вместе с формами и POST-запросами:

- регистрация макета на согласование;
- добавление комментария клиента;
- отправка макета на доработку и утверждение макета;
- добавление дизайнеров и клиентов.

## Возможности консольной версии

- просмотр списка макетов с сортировкой по сроку согласования;

## Назначение модулей

- `manage.py` — запуск команд управления Django-проектом
  (`runserver`, `check`, `migrate`, `startapp`);
- `layout_service/` — пакет настроек Django-проекта:
  `settings.py` — настройки (приложения, каталог шаблонов `DIRS`,
  язык, часовой пояс, режим отладки), `urls.py` — маршрутизация верхнего уровня и
  `handler404`, `asgi.py` и `wsgi.py` — точки взаимодействия с
  сервером;
- `templates/` — шаблоны уровня проекта: базовый шаблон, страница
  404 и навигация;
- `homepage/` — Django-приложение главной страницы: view-функции
  `index()` и `page_not_found()`, шаблон главной и собственные
  статические файлы проекта;
- `layouts/` — Django-приложение макетов: view-функции `layouts()`,
  `layout_detail()`, `search()`, `overdue()` и `statistics()`,
  маршруты в `urls.py`, шаблоны в `templates/layouts/`;
- `comments/` — Django-приложение комментариев: view-функции
  `comments()` и `comment_detail()`, маршруты в `urls.py`, шаблоны в
  `templates/comments/`;
- отдельное приложение для дизайнеров и клиентов не создавалось:
  участники отображаются в карточках макетов и комментариев, а работа
  с пользователями будет реализована вместе с аутентификацией;
- `models.py` Django-приложений пока пуст: Django-модели появятся при
  переходе на Django ORM (не путать с пакетом `models/` из ПР3);
- `db/database.py` — путь к базе `data/layout_service.sqlite`,
  функция `get_connection()` (настройка `row_factory = sqlite3.Row`
  и `PRAGMA foreign_keys = ON`) и `create_tables()`;
- `db/import_json.py` — перенос данных из JSON-файлов в таблицы;
- `db/shell.py` — мини-консоль для выполнения SQL-запросов, если
  программа SQLite CLI не установлена;
- `sql/schema.sql` — SQL-команды создания таблиц;
- `sql/queries.sql` — проверенные SQL-запросы проекта;
- `main.py` — консольная версия (сохранена с ПР3): меню, ввод данных,
  пользовательские сценарии;
- `models/participants.py` — классы `Participant`, `Designer`,
  `Client` и функции работы с их коллекциями;
- `models/layouts.py` — класс `Layout` и функции обработки коллекции
  макетов (поиск, фильтрация, сортировка, статистика);
- `models/comments.py` — класс `Comment` и функции работы с
  комментариями, в том числе `get_comment_by_id()` (добавлена в ПР5
  для страницы комментария);
- `models/__init__.py` — импорт классов из пакета `models`;
- `storage.py` — загрузка и сохранение данных: JSON → объекты и
  объекты → JSON;
- `utils.py` — безопасный ввод строк, чисел и дат;
- `tests/` — автоматизированные тесты проекта.

## Хранение данных

Исходные данные хранятся в каталоге `data/` в формате JSON (их
использует консольная версия; веб-версия с ПР7 читает данные из
SQLite, см. следующий раздел). При загрузке
записи преобразуются в объекты `Designer`, `Client`, `Layout` и
`Comment`, при сохранении объекты преобразуются обратно в данные.

`data/layouts.json`:

        "id": 1,
        "title": "Главная страница интернет-магазина",
        "version": 2,
        "designer_id": 1,
        "client_id": 1,
        "sent_date": "2026-09-10",
        "approval_days": 5,
        "status": "На доработке"

`data/comments.json`:

    {
        "id": 1,
        "layout_id": 1,
        "author_id": 1,
        "text": "Увеличить логотип",
        "date": "2026-09-13",
        "layout_version": 1

## База данных SQLite (ПР7)

Данные проекта перенесены из JSON-файлов в базу
`data/layout_service.sqlite`. JSON-файлы остаются в проекте как
исходные данные и используются консольной версией.

### Структура таблиц

| Таблица | Поля и типы | Ключи |
|---------|-------------|-------|
| `designers` | `id INTEGER`, `name TEXT`, `email TEXT` | PK `id` |
| `clients` | `id INTEGER`, `name TEXT`, `email TEXT`, `company TEXT` | PK `id` |
| `layouts` | `id INTEGER`, `title TEXT`, `version INTEGER`, `designer_id INTEGER`, `client_id INTEGER`, `sent_date TEXT`, `approval_days INTEGER`, `status TEXT` | PK `id`; FK `designer_id` → `designers.id`, FK `client_id` → `clients.id` |
| `comments` | `id INTEGER`, `layout_id INTEGER`, `author_id INTEGER`, `text TEXT`, `comment_date TEXT`, `layout_version INTEGER` | PK `id`; FK `layout_id` → `layouts.id`, FK `author_id` → `clients.id` |

Связи: у дизайнера и клиента может быть много макетов, у макета —
много комментариев (связи «один ко многим»). Даты хранятся в формате
ISO `ГГГГ-ММ-ДД`, срок согласования вычисляется запросом:
`date(sent_date, '+' || approval_days || ' days')`.

### Создание базы и перенос данных

Таблицы описаны в `sql/schema.sql` (`CREATE TABLE IF NOT EXISTS`,
поэтому скрипт можно запускать повторно). Создание таблиц и перенос
данных выполняются одной командой из корня проекта:

    python -m db.import_json

Скрипт создаёт таблицы, очищает их и заполняет данными из JSON через
`executemany()` с параметрами `?`. Порядок импорта: `designers`,
`clients`, `layouts`, `comments` — сначала таблицы, на которые
ссылаются внешние ключи. При ошибке выполняется `rollback()`.

### SQL-запросы

Файл `sql/queries.sql` содержит 15 запросов с комментариями:

- выборка списков: все макеты, список дизайнеров;
- фильтрация `WHERE`: макеты по статусу, поиск по названию (`LIKE`),
  просроченные макеты на дату;
- соединение таблиц `JOIN`: макеты с дизайнером и клиентом,
  комментарии с макетом и автором;
- агрегатные функции `COUNT()`: всего макетов, макетов в ожидании
  ответа, комментариев к макету;
- группировка `GROUP BY`: макеты по статусам, макеты по дизайнерам,
  комментарии по макетам;
- фильтрация групп `HAVING`: макеты с заданным минимумом
  комментариев;
- подзапрос `NOT IN`: макеты без комментариев.

Проверить запросы можно в SQLite CLI (`sqlite3
data/layout_service.sqlite`) или во встроенной мини-консоли:

    python -m db.shell

### Данные из SQLite на страницах сайта

View-функции открывают соединение `get_connection()`, выполняют
SQL-запрос, получают строки `sqlite3.Row` и передают их в шаблон
через контекст. Значения, полученные от пользователя (строка поиска,
статус, дата, минимум комментариев), передаются в запрос
параметрами `?` и не подставляются в текст SQL.

| Страница | Запросы |
|----------|---------|
| `/` | `COUNT(*)`, `GROUP BY status` |
| `/layouts/` | `JOIN` трёх таблиц |
| `/layouts/<id>/` | `JOIN` + `WHERE id = ?`, комментарии макета |
| `/layouts/search/` | `WHERE title LIKE ? AND status = ?` |
| `/layouts/overdue/` | `WHERE status != 'Утверждён' AND срок < ?` |
| `/layouts/statistics/` | `COUNT`, `GROUP BY`, `LEFT JOIN`, `HAVING`, `NOT IN` |
| `/comments/`, `/comments/<id>/` | `JOIN` комментариев, макетов и клиентов |

## Проверка качества кода

Проверка выполняется из корня проекта одной командой:

    flake8

Вместе с основным линтером запускаются его плагины: pep8-naming
проверяет имена классов, функций и переменных, flake8-isort —
порядок импортов. Отсутствие вывода означает отсутствие замечаний.

Автоматически исправить порядок импортов:

    isort .

## Форматирование кода

Посмотреть, что форматтер предлагает изменить, не трогая файлы:

    autopep8 --diff --recursive .

Применить форматирование:

    autopep8 --in-place --recursive .

Форматтер использует те же настройки из `setup.cfg` (секция `[pep8]`),
что и линтер, поэтому их требования не расходятся.

## Проверка аннотаций типов

    mypy .

Проверяет, что фактические типы значений соответствуют аннотациям
в сигнатурах функций и методов. Программу не запускает — анализирует
исходный код.

Реализовано (ПР5):

  `layouts`, `comments`);

- страницы переведены на шаблоны Django и `render()`, функция
  `page()` удалена;
- базовый шаблон `base.html`, наследование `{% extends %}` и блоки
  `{% block %}`;
- включаемые шаблоны `{% include %}`: навигация, карточка и статус
  макета, строка комментария;

- пространства имён `app_name` и ссылки `{% url %}`;
- фильтры `length`, `default`, `date`, `truncatechars`;
- собственные статические файлы: CSS, JavaScript и логотип.

Реализовано (ПР7):

- спроектирована база данных: таблицы `designers`, `clients`,
  `layouts`, `comments`, первичные и внешние ключи;

  скриптом `sql/schema.sql`;

- SQL-запросы сохранены в `sql/queries.sql`;
